so basically, here is how it works
alice and bob both generate private keys which they keep private, and drive public keys from them which they share openly. typically this is initialized in the app server backend.
alice and bob then start a communication session, they generate an aes and mac key
alice then makes a message she wants to send to bob. she then generates an iv, and encrypts the message into cyphertext with the aes. the encryption process is randomized with the iv in order to ensure that sending the same message twice in the session will not generate the same cyphertext.
an rsa is then generated by encrypting the aes and mac together, locking it with bob's public key.
the sender id, reciever id, rsa, iv, and cyphertext are all then algorithmically processed to create the hmac, which is used to ensure data integrity. the sender id, reciever id, rsa, iv, cyphertext, and hmac are then placed into a json file and sent to bob
bob then is able to decript the rsa with his private key, producing the aes and mac. he then uses then produces his own hmac with the data in the json and the mac. if his hman and the hmac sent over the json match then he knows the message is secure. he can then decrypt the cyphertext using the aes.
if eve intercepts the message, she cannot read anything because the linchpin of the message is bob's private key. As long as she does not have that private key, the only thing she can do is corrupt the data. typically this will target the cyphertext portion, but it can be done to any of the data being transmited. however, doing so will result in bob's recieved hmac not matching his generated hmac so he will know that the message has had its integrity compromized
